# Tuesday 1 September

Q4 planning kicks off today. Nothing is decided; this is the brainstorm, written straight into a list as people talked,
and the structure is whatever the conversation did to it. The cleaned-up version goes into
[Q4 OKRs](../projects/q4-okrs.md), and the version that will be committed is in
[the product repository](../../work/product/okrs/2026-q4.md).

## Brainstorm

- Make route sharing the headline of Q4
  * Sharing by link
    + Link opens in the app if it is installed
      - Link opens on the web if not
        * Web view is read-only
          + Web view has a button that says "open in Kestrel", and the button has to work on both phone platforms
  * Sharing a ride after the ride
    + The ride's summary becomes a card
- Offline sync stops being a project and becomes a property
  * Every feature answers the question "what does this do with no network?"
    + Nobody ships a screen without the answer
- Hiring
  * One backend engineer, for the sync team
  * One designer, if Tomás agrees that is the right order

Tight list above: no blank lines between items. The loose one is the same brainstorm after Priya asked for room to
write comments next to the items.

- Reliability

  What is the number we are willing to be paged for?

- Growth

  Route sharing is the growth lever, so the OKR should name a number of shared routes opened by non-members.

- Cost

  The tile bill went up after the offline pack; somebody should own it.

## Key results, drafted

1. Ship route sharing to everyone by the end of October, with the web fallback working on both mobile platforms and
   the desktop browser, and with a measurable path from a shared link to an installed app
   1. Web fallback for shared links on every platform that we claim to support in the help centre, including the older
      browsers that Jo says a surprising number of members still use
      1. A link opened on the desktop browser shows the route on a map, with the elevation profile, the distance and
         the surface breakdown, and offers to send the link to a phone
         1. The offer to send it to a phone must not ask for an email address, because we do not want to keep one
            1. If the phone is on the same account the route simply appears there, and that case needs a test that
               does not need two real phones
2. Cut the offline sync failure rate in half
   1. Define the failure rate first, because right now there are three definitions in three dashboards
3. Fill the backend role

## Decisions so far

101. Keep the Q3 key results that are not done, as carry-over, and label them so

     They are not new work, and the label is how Priya will see it at the quarterly review.

     Carry-over items stay in the same note until they are closed.

102. Do not add a fifth objective

     Four is already more than we can hold in our heads.

     ```text
     objectives: reliability, sharing, growth, hiring
     ```

103. Review the OKRs again on the first Friday of October

     > We can change the numbers. We should not change the objectives.
